# 모바일 앱(Play 스토어 / App Store) 이식 계획

> 작성: 2026-08-05 · 대상 커밋 `0e05c49` · 오너 지시("지금 만든 프로그램을 그대로 앱으로")에 대한 코드 기준 실사 결과
> **결론: 가능하다.** 방식은 **Capacitor**(현재 웹 빌드를 iOS/Android 네이티브 셸로 감싸기).
> React Native·Flutter 재작성 불필요. 다만 "그대로"는 아니고 아래 P0 항목은 반드시 손봐야 한다.

## 왜 Capacitor인가
현 구조가 `React+Vite 웹앱`을 `Electron 셸`이 감싸는 형태라, 같은 웹 빌드를 모바일 셸로
한 번 더 감싸는 것이 자연스럽다. 화면 코드·상태관리·NAS REST 연동은 전부 재사용된다.
서버(NAS)는 손댈 것이 없다.

## 🔧 반드시 고쳐야 하는 것

### P0 — 데이터 유실·기능 파손 (착수 전 필수)

**1. 사진·오프라인 큐·로그인 토큰이 전부 localStorage에 있다**
- 사진: `photoStore.ts:16` — 1280px JPEG **base64**를 엔티티당 1키로 저장 (장당 200~400KB)
- 상담 사진: `consultationStore.ts` + `types:322` — 레코드 배열 통짜에 base64 혼입
- 미전송 큐: `nasOutbox.ts:13` / 인증 토큰: `authApi.ts:32`
- **문제**: 모바일 WebView의 localStorage는 오리진당 대략 5~10MB이고, **iOS는 저장공간이 부족하면 website data를 통째로 삭제할 수 있다.** 사진 15~25장이면 포화되고, 그 시점에 **미전송 매출·시술 기록과 로그인 세션이 함께 증발**한다.
- **조치**: 사진 → `@capacitor/filesystem`(또는 IndexedDB), 큐 → IndexedDB, 토큰 → `@capacitor/preferences`/Keychain. 총량 가드(`navigator.storage.estimate()`)와 장수 상한도 함께.
- 참고: 현재 가드는 `store.ts:74` `safeSetItem`의 **quota 초과 "감지·경고"뿐**이고 정리·예방 로직은 없다.

**2. 엑셀·PDF 내보내기가 iOS에서 아무 반응 없이 죽는다**
- `dataExport.ts:319` `XLSX.writeFile()`, `pdfExport.ts:82` `doc.save()`
- 둘 다 내부적으로 `<a download>`를 쓰는데 **iOS WKWebView는 download 속성을 무시**한다. 오류도 안 나고 그냥 아무 일이 없다 — 사용자 입장에서 최악의 버그 유형.
- **조치**: `XLSX.write({type:'base64'})` / `doc.output('datauristring')` → Filesystem 저장 → `@capacitor/share`로 넘기기.

**3. 빌드 설정 3종**
- `vite.config.ts:159` base가 `'/'` → 커스텀 스킴에서 asset 로드 실패. `BUILD_TARGET=capacitor → './'` 분기 필요 (v1.0.43 흰화면 사고와 동일 계열).
- `vite.config.ts:56` PWA/Service Worker가 Electron 빌드에서만 꺼짐 → 모바일에서도 꺼야 함(앱 번들 ↔ SW 이중 캐시 충돌).
- `vite.config.ts:20` CSP에 `capacitor://localhost`·`https://localhost` 추가, 죽은 `http://127.0.0.1:19876` 제거.

## 심사 통과 전략

**Apple 4.2 (최소 기능)** — "웹사이트를 감싸기만 한 앱"은 반려된다. 아래 네이티브 요소를
실제로 넣어 앱다움을 확보한다. 대부분 우리 업무에 자연스럽게 필요한 것들이다.
- 카메라 촬영(시술 전후 사진) — `@capacitor/camera`
- 오프라인 사용(이미 outbox 구조 있음) — 스토리지 이전과 함께 홍보 포인트화
- 예약 리마인더 로컬 알림 — `reminderEngine.ts` 로직 재활용
- 시스템 공유 시트(엑셀/PDF 내보내기) — P0-2와 동시 해결

**배포 경로** — 제휴 매장 전용 B2B 도구이므로:
1. **Unlisted(비공개 목록)** — 스토어에 있으나 검색 노출 없음, 링크로만 설치. **권장**
2. Apple Business Manager 커스텀 앱 — 조직 지정 배포, 4.2 심사 사실상 우회
3. 일반 공개 — 4.2 심사가 가장 빡셈

**건강 앱 신고** — Play는 건강 앱 선언 양식 작성 필요. AI 피부분석은 진단·치료 권장으로
읽히면 의료기기 소프트웨어(SaMD)로 분류되니 **"관리 참고용" 톤을 유지**한다(의료법 27조 대응과 동일 기조).

**개인정보** — 고객 PII + 피부상태·시술기록은 민감정보. 개인정보처리방침 URL 필수,
Play 데이터 안전 양식 작성, iOS Info.plist 권한 사유 문구(`NSCameraUsageDescription` 등) 필요.

# 오너 확정 사항 (2026-08-05 논의)

## D1. 개발·배포 순서
PC 버전에서 먼저 수정·업데이트 → 이후 모바일 앱을 모바일 반응형으로 따라붙임.
같은 코드베이스라 구조적으로 그렇게 되지만, **배포 속도가 달라 버전이 벌어지는 구간이 항상 생긴다**
(PC=인앱 즉시 / 모바일=심사 1~3일~2주).

**→ 규칙**: 서버 데이터 API는 **필드 추가만 허용, 제거·개명 금지**.
(`docs/DISTRIBUTION-POLICY.md` 규칙4를 데이터 API에도 동일 적용)
서버가 `minSupportedVersion`을 내려 구버전 앱에 업데이트 안내를 띄운다.

## D2. 기능 범위 (1차)
| | 모바일 (현장) | PC (사무) |
|---|---|---|
| 주력 | 사진 촬영, 상담 노트, 오늘 예약, 시술 완료 처리, 결제 요청 발송 | 손익계산서, 매출·지출, 제품·재고, 직원, 설정, 엑셀 내보내기 |
| 양쪽 | 고객 조회·등록, 예약 확인 | 좌동 |
| 차단 | 어드민 콘솔, 구독/결제 설정 | — |

1차는 위 표대로. 이후 사용 데이터를 보고 확장한다.

## D3. 상담 노트
**기존 `consultations`(NAS 저장, 계정별 분리)를 그대로 쓰고 입력 UI만 모바일용을 추가한다.**
새 저장소를 만들지 않는다 — 만들면 "모바일에서 적은 게 PC에서 안 보임"이 된다.
- 모바일: 노트형(자유 서술 + 빠른 태그), 고객 앞에서 대화하며 적을 수 있는 무게
- PC: 현재의 구조화 폼 유지
- 저장 위치·데이터 구조는 동일

## D4. 임상 사진 — **저장 정책 변경**
**촬영한 기기에만 저장하는 것을 기본으로 하고, 지점이 저장 방식을 선택할 수 있게 한다.**
본사(NAS)가 전 지점의 고객 얼굴 사진을 전부 보관하지 않는다.

- 촬영 가이드와 함께 촬영해 **임상사진으로서 값어치가 있게** 남긴다
  (직전 사진 반투명 오버레이 → 같은 각도·거리로 촬영. 전/후 비교가 실제로 쓸 수 있게)
- 기기 용량에 따라 지점이 보관량·보관 기간을 선택
- **개인정보 측면 이점**: 본사가 민감정보(얼굴·피부 상태 사진)를 보유하지 않아 위험이 줄어든다

> ⚠️ **미해결 — D4와 "PC·모바일 데이터 호환" 요구가 상충한다.**
> 사진이 촬영 기기에만 있으면 PC와 모바일을 함께 쓰는 지점에서 서로 안 보인다.
> 아래 3안 중 택일 필요 (권장: A안).
>
> | 안 | 내용 | 장단 |
> |---|---|---|
> | **A. 지점 선택 (권장)** | 기본=기기 저장만. 설정에서 "지점 기기 간 사진 공유"를 켜면 그 지점만 NAS 동기화 | 오너 의도에 가장 부합. 본사 부담은 켠 지점만. 구현 단순 |
> | B. 썸네일만 공유 | 작은 미리보기는 NAS, 원본은 촬영 기기 | PC에서 목록·비교는 되고 용량은 적음. 구현 복잡 |
> | C. 용량 쿼터 | NAS 보관하되 지점당 상한 + 오래된 것 자동 삭제 | 호환 완전. 본사 보관 부담은 남음 |
>
> **A안 채택 시 반드시 함께 처리할 것**
> 1. **기기 분실·교체 시 임상사진 영구 소실** — 매장에 명확히 고지 + 기기에서 사진 일괄 내보내기 기능 제공
> 2. **기존 지점 회귀 주의** — 현재는 NAS 동기화가 켜진 상태로 동작 중(박재영에스테틱·아르케스파). 기본값을 바꾸면 기존 사진 접근이 끊긴다. **기존 지점은 "공유 켬"으로 마이그레이션**하고, 신규 설치만 기본 끔.

## D5. 사진 저장 방식 통합
상담 사진(레코드 내 base64)과 시술 사진(photoStore 별도 키)이 지금 다른 방식이다.
**모바일 작업 때 함께 통합**한다. 통합 시 D4 정책을 적용한 단일 경로로 만든다.

## D6. 모바일 업데이트 전달 방식 — **2단 구조**

| 구분 | 대상 | 동작 |
|---|---|---|
| **큰 업데이트** (네이티브 변경) | 플러그인 추가·권한 변경·네이티브 코드 수정·앱 기능의 실질적 변경 | 앱 안에 **안내 배너만** 표시 → 누르면 **스토어 앱 페이지로 자동 이동**해서 사용자가 업데이트 버튼을 누름 |
| **작은 업데이트** (웹 자산만) | 화면·문구·버그 수정 등 JS/CSS/HTML 변경 | 앱 안에 배너 표시 → **배너만 눌러도 바로 적용**(OTA 번들 교체, 재설치 없음) |

**규정 확인 완료**: Apple은 WebKit/JavaScriptCore가 실행하는 **JS·에셋의 OTA 교체를 명시적으로 허용**한다
(구 3.3.2, 2025년 개편 후 3.3.1(B)). 단 **앱의 본래 목적을 바꾸거나 심사를 우회하는 용도는 금지**.
Google Play도 유사하다.

**→ 경계선 (이대로 지킨다)**
- OTA 가능: 화면 수정, 문구, 버그픽스, 기존 기능의 개선
- 스토어 필수: 새 네이티브 권한(카메라 등), 플러그인 추가, 새로운 성격의 기능, 결제 관련 변경

**→ 구현 방식**: 지금 PC에서 쓰는 업데이트 채널(`latest.json`)과 **같은 패턴을 재사용**한다.
서버가 `mobile-latest.json`으로 `minSupportedVersion`(스토어 강제) / `bundleVersion`(OTA) /
스토어 딥링크(`itms-apps://`, `market://`)를 함께 내려준다.
